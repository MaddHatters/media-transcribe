### ⚡ MEDIUM RISK (Fix Soon)

#### Issue #1: `_emergency_stop_engine()` called on every pipeline completion via `finally`

**Description**: The plan specifies placing `_emergency_stop_engine()` in the `except` block only, but the implementation uses a `finally` block. This means on every successful pipeline run, `is_recording()` makes a WebSocket API call to OBS to check recording status. The call is harmless (it's a no-op when not recording) but adds unnecessary latency and network traffic on every successful run.

**Location**:
- File: `src/pipeline/runner.py`
- Lines: `91-95`

**Offending Code**:
```python
except BaseException:
    log.critical("PIPELINE FAILED — stopping OBS recording", exc_info=True)
    raise
finally:
    self._emergency_stop_engine()
```

**Recommended Solutions**:
1. **Move cleanup into `except` block only** (Preferred)
   - Move `self._emergency_stop_engine()` into the `except BaseException` block before `raise`
   - Rationale: Matches plan design; avoids unnecessary OBS API calls on success

2. **Keep `finally` but guard with a flag**
   - Set `_had_exception = True` in the except block, only call cleanup if flag is set
   - Trade-off: More defensive but adds a mutable flag

#### Issue #2: Parent process registers OBS atexit/signal handlers when backgrounding

**Description**: `setup_logging()` is called in `main()` before the background/foreground decision. It registers `_emergency_stop_obs` as an atexit handler and installs signal handlers. When the parent process exits after spawning the child, the atexit hook attempts a WebSocket connection to OBS. This is harmless (fails silently on Linux devbox; is a no-op on Windows when not recording) but produces unnecessary network activity and could produce confusing debug output.

**Location**:
- File: `cli.py`
- Lines: `166-176`
- File: `src/logging_config.py`
- Lines: `33-41`

**Offending Code**:
```python
# cli.py:166-168 — setup_logging called before background decision
is_foreground = getattr(args, "foreground", False) or args.command not in LONG_RUNNING_COMMANDS
from src.logging_config import setup_logging
log_path = setup_logging(args.command, foreground=is_foreground)

# Then at line 170-176, the process backgrounds (but atexit is already registered)
if args.command in LONG_RUNNING_COMMANDS and not getattr(args, "foreground", False):
    ...
    return background_relaunch(args, log_dir)
```

**Recommended Solutions**:
1. **Split `setup_logging` into logging-only and crash-guard registration** (Preferred)
   - `setup_logging()` configures file/console handlers only
   - A separate `install_crash_guards()` is called only in foreground mode (the child process)
   - Rationale: Parent doesn't need crash guards; child needs all of them

2. **Unregister atexit in parent before spawning child**
   - Call `atexit.unregister(_emergency_stop_obs)` in the background branch before returning
   - Trade-off: Simpler but still installs/uninstalls signal handlers unnecessarily

#### Issue #3: Three log files created per background pipeline run

**Description**: A single background pipeline invocation creates three log files:
1. Parent's Python logging file (from `setup_logging` in `main()`) — nearly empty
2. Child's stdout/stderr capture file (from `background_relaunch`'s `open(log_file, "w")`)
3. Child's Python logging file (from `setup_logging` in child's `main()`)

Files #2 and #3 both contain the child's logging output (since the child runs in foreground mode with both FileHandler and StreamHandler, and stderr is redirected to file #2).

**Location**:
- File: `cli.py`
- Lines: `45, 168`

**Recommended Solutions**:
1. **Have the child use the same log file for Python logging and stdout capture**
   - Pass the `background_relaunch` log file path to the child via an env var or CLI arg
   - Child's `setup_logging` uses that path instead of generating a new one

#### Issue #4: Signal handler double-calls `_emergency_stop_obs`

**Description**: `_signal_handler` calls `_emergency_stop_obs()` directly, then calls `sys.exit()` which raises `SystemExit`, triggering atexit handlers — including `_emergency_stop_obs` which was registered by `setup_logging`. This results in two OBS WebSocket connections on signal receipt.

**Location**:
- File: `src/logging_config.py`
- Lines: `65-68`

**Offending Code**:
```python
def _signal_handler(signum, frame):
    _emergency_stop_obs()  # first call
    logging.warning("[crash-guard] Received signal %s, exiting", signal.Signals(signum).name)
    sys.exit(128 + signum)  # triggers atexit → second call
```

**Recommended Solutions**:
1. **Unregister before exiting**
   - Add `atexit.unregister(_emergency_stop_obs)` before `sys.exit()`
   - Rationale: Prevents double OBS connection; clean shutdown path

#### Issue #5: `STALL_THRESHOLD` changed from 6 to 3 without explicit plan instruction

**Description**: The plan states "stall_count is fine for its nudge purpose" but the implementation lowers `STALL_THRESHOLD` from 6 to 3. This change is actually necessary: with `STUCK_THRESHOLD=5` and the original `STALL_THRESHOLD=6`, the stuck-detection would abort before nudging is ever attempted (stuck fires at poll 5, nudge wouldn't fire until poll 7). Lowering to 3 ensures one nudge attempt (at poll 4) before the stuck-abort (at poll 5). This is a correct design decision.

**Location**:
- File: `src/capture/recorder.py`
- Line: `18`

**Recommended Solutions**:
1. **No change needed** — the value is correct for the new stuck-detection logic to coexist with nudging. Document the relationship between STALL_THRESHOLD and STUCK_THRESHOLD if desired.
