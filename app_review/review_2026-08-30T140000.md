#### Issue #2: `_check_patreon_session` only checks credential existence

**Description**: The plan explicitly states this gate "delegates to `PatreonSource.authenticate()`" which navigates to patreon.com and checks for a login form. The actual implementation only calls `read_credential("patreon_02_ai")` to check if credentials exist in Windows Credential Manager. This conflates "credentials are stored" with "session is valid" — a user could have valid credentials but an expired Patreon session.

**Location**:
- File: `src/capture/preflight.py`
- Lines: `147-158`

**Offending Code**:
```python
def _check_patreon_session(self) -> bool:
    try:
        from src.capture.credentials import read_credential
        creds = read_credential("patreon_02_ai")
        if creds:
            log.info("Patreon credentials available")
            return True
        log.warning("No Patreon credentials found")
        return False
    except Exception as exc:
        log.error("Patreon session check failed: %s", exc)
        return False
```

**Recommended Solutions**:
1. **Delegate to `PatreonSource.authenticate()`** (Preferred)
   - Requires making `run_all` or `_check_patreon_session` async (or wrapping with `asyncio.run`)
   - Create/accept a CDPClient parameter
   - Rationale: Matches plan, catches expired sessions before a multi-hour batch run

2. **Rename to `_check_patreon_credentials`**
   - At minimum, rename to accurately reflect what it does
   - Add a separate `_check_patreon_session` that actually validates via CDP
   - Trade-off: Less intrusive change, but still leaves the session gap

#### Issue #4: Blocking `subprocess.run` in async `get_posts()`

**Description**: `YouTubeSource.get_posts()` is an `async def` method that calls `subprocess.run(...)` with a 60-second timeout. This blocks the event loop for the entire duration of the yt-dlp catalog operation, preventing any concurrent async work.

**Location**:
- File: `src/sources/youtube.py`
- Lines: `27-29`

**Offending Code**:
```python
async def get_posts(self, cdp: CDPClient, query: str | None = None) -> list[Post]:
    ...
    proc = subprocess.run(
        ["uvx", "yt-dlp", "--flat-playlist", "-J", query],
        capture_output=True, text=True, timeout=60,
    )
```

**Recommended Solutions**:
1. **Use `asyncio.to_thread`** (Preferred)
   - Wrap the `subprocess.run` call in `await asyncio.to_thread(subprocess.run, ...)`
   - Rationale: Minimal change, moves the blocking call to a thread

2. **Use `asyncio.create_subprocess_exec`**
   - Replace `subprocess.run` with the async subprocess API
   - Trade-off: More code change but fully async

#### Issue #6: `OBSEngine.start()` blocks with `time.sleep(2)`

**Description**: `OBSEngine.start()` calls `time.sleep(2)` to let OBS stabilize after starting recording. Since the Recorder calls `self.engine.start(filename)` inside an async method, this 2-second sleep blocks the entire event loop.

**Location**:
- File: `src/engines/obs_engine.py`
- Lines: `56`

**Recommended Solutions**:
1. **Document the sync nature and use `await asyncio.to_thread()` in Recorder**
   - The plan notes engines are sync by design; the Recorder should wrap the `start()` call
   - Rationale: Keeps the engine protocol simple while being event-loop friendly

**Location**:
- File: `src/engines/ytdlp_engine.py`
- Lines: `37-42`

**Recommended Solutions**:

   - Rationale: Recorder's exception handler will catch it, but the error message should be actionable
