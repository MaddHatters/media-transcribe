### ⚠️ HIGH RISK (Should Fix Before Merge)

#### Issue #1: `main()` ignores `background_relaunch()` return code — child failure reports success

**Description**: `background_relaunch()` returns `proc.returncode` (non-zero) when the child dies immediately (line 64), but `main()` discards the return value and unconditionally returns 0 (line 177). This means: the parent prints `"ERROR: child exited immediately with code X"` to the console, then exits with code 0. For SSH callers, exit 0 = success. The startup-verification feature (the `time.sleep(1) + poll()` block added on lines 60-64) is the right idea, but its result is silently thrown away.

**Location**:
- File: `cli.py`
- Lines: `176-177`

**Offending Code**:
```python
        background_relaunch(args, log_dir)
        return 0
```

**Recommended Solutions**:
1. **Propagate the return code** (Preferred)
   - Change to: `rc = background_relaunch(args, log_dir); return 1 if rc is not None and rc != 0 else 0`
   - Or more directly: `return background_relaunch(args, log_dir) or 0` — but this conflates PID-as-success with zero, which is confusing. Better to have `background_relaunch` return 0 on success and non-zero on failure.
   - Rationale: The whole point of the startup verification is to detect immediate child death. Swallowing the result undermines the fix.

2. **Refactor `background_relaunch` to always return 0/1** (Cleaner)
   - Have the function return 0 on success, 1 on failure (instead of returning the PID on success and return code on failure). Print the PID inside the function (already done). Then `main()` can do `return background_relaunch(args, log_dir)`.
   - Trade-off: Changes the return contract but makes intent explicit.

#### Issue #4: Pipeline uses `except Exception` instead of `finally` — misses `BaseException`

**Description**: The plan specifies a `try/finally` block to ensure OBS cleanup on ANY unhandled exception. The implementation uses `try/except Exception/raise`, which catches `Exception` subclasses but not `KeyboardInterrupt`, `SystemExit`, or `asyncio.CancelledError` (a `BaseException` in Python 3.9+). The signal handlers in `logging_config.py` partially cover `SIGINT`/`SIGTERM`, but there's a gap: `asyncio.CancelledError` inside the event loop won't trigger the signal handler, and `SystemExit` from programmatic calls won't either.

**Location**:
- File: `src/pipeline/runner.py`
- Lines: `91-94`

**Offending Code**:
```python
        except Exception:
            log.critical("PIPELINE FAILED — stopping OBS recording", exc_info=True)
            self._emergency_stop_engine()
            raise
```

**Recommended Solutions**:
1. **Use `finally` with a guard** (Preferred)
   ```python
   failed = False
   try:
       ...
   except Exception:
       failed = True
       log.critical("PIPELINE FAILED — stopping OBS recording", exc_info=True)
       self._emergency_stop_engine()
       raise
   finally:
       if failed:
           pass  # already handled above
       # Or unconditionally call cleanup for BaseException cases
   ```
   - A simpler approach: just use `except BaseException` instead of `except Exception`.

2. **Accept the gap — document it**
   - The signal handlers cover Ctrl+C and SIGTERM. `asyncio.CancelledError` in a pipeline context is rare. The risk is low enough to accept.
   - Trade-off: Orphaned recordings possible in edge cases.

#### Issue #5: Double OBS stop call on signal exit

**Description**: `_signal_handler` calls `_emergency_stop_obs()` directly, then calls `sys.exit()`, which triggers `atexit` handlers — causing `_emergency_stop_obs()` to run a second time. Both calls are wrapped in try/except so this won't crash, but it creates a redundant OBS WebSocket connection attempt on every signal-driven exit.

**Location**:
- File: `src/logging_config.py`
- Lines: `66-69`

**Offending Code**:
```python
def _signal_handler(signum, frame):
    _emergency_stop_obs()
    logging.warning("[crash-guard] Received signal %s, exiting", signal.Signals(signum).name)
    sys.exit(128 + signum)
```

**Recommended Solutions**:
1. **Add a module-level guard flag**
   ```python
   _obs_cleanup_done = False
   def _emergency_stop_obs():
       global _obs_cleanup_done
       if _obs_cleanup_done:
           return
       _obs_cleanup_done = True
       ...
   ```

#### Issue #6: `setup_logging` accumulates handlers on repeated calls

**Description**: Each call to `setup_logging()` adds a new `FileHandler` (and optionally `StreamHandler`) to the root logger without checking for existing handlers. In production this is harmless (called once), but in tests, repeated calls leak handlers and produce duplicate log output. The test teardown code manually removes added handlers, but a defensive check would be cleaner.

**Location**:
- File: `src/logging_config.py`
- Lines: `19-31`

**Recommended Solutions**:
1. **Guard against re-initialization**
   - Add `if root.handlers: return log_file` at the top, or clear existing handlers first.
   - Trade-off: May mask bugs where `setup_logging` is called in unexpected contexts.
