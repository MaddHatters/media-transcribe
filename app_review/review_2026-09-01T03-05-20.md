#### Issue #1: Pipeline uses `except Exception` instead of `finally` for OBS cleanup

**Description**: The spec requires "Add a `finally` block to the pipeline that cleans up even on unhandled exceptions." The implementation uses `except Exception: ... raise` which does not catch `KeyboardInterrupt` or `SystemExit`. When a user sends SIGINT during a pipeline run, the custom signal handler calls `_emergency_stop_obs()` which creates a *new* OBSEngine instance — it does not use the pipeline's already-connected engine. While the signal handler provides coverage, the pipeline should also clean up its own engine via `finally` as specified, providing defense-in-depth.

**Location**:
- File: `src/pipeline/runner.py`
- Lines: `73-94`

**Offending Code**:
```python
        try:
            for i, post in enumerate(queue):
                ...
        except Exception:
            log.critical("PIPELINE FAILED — stopping OBS recording", exc_info=True)
            self._emergency_stop_engine()
            raise
```

**Recommended Solutions**:
1. **Add `finally` block alongside `except`** (Preferred)
   - Keep the `except Exception` for logging, add a `finally` for cleanup:
   ```python
   try:
       for i, post in enumerate(queue):
           ...
   except Exception:
       log.critical("PIPELINE FAILED — stopping OBS recording", exc_info=True)
       raise
   finally:
       self._emergency_stop_engine()
   ```
   - Rationale: Matches spec, catches `KeyboardInterrupt`/`SystemExit`, `_emergency_stop_engine` is safe to call even when not recording (checks `is_recording()` first).

2. **Keep current code, document the gap** (If timeline is tight)
   - Signal handlers + atexit provide overlapping coverage. Add a comment noting this is intentional because signal handler already handles SIGINT.
   - Trade-off: Deviates from spec, relies on a separate mechanism for cleanup.

#### Issue #2: Atexit handler uses private `engine._client` attribute

**Description**: `_emergency_stop_obs()` in `logging_config.py` accesses `engine._client.get_record_status()` directly instead of using the public `engine.is_recording()` method. `OBSEngine.is_recording()` does exactly the same thing (`self._client.get_record_status().output_active`) but also handles the case where `_client` is `None` and falls back to `self._recording`. If `OBSEngine` refactors its internals, the atexit handler would break silently (caught by `except Exception: pass`).

**Location**:
- File: `src/logging_config.py`
- Lines: `51-63`

**Offending Code**:
```python
def _emergency_stop_obs():
    try:
        from src.engines.obs_engine import OBSEngine
        engine = OBSEngine()
        engine.connect()
        status = engine._client.get_record_status()
        if status.output_active:
            engine.stop()
            logging.warning("[crash-guard] Stopped orphaned OBS recording")
        engine.disconnect()
    except Exception:
        pass
```

**Recommended Solutions**:
1. **Use public `is_recording()` API** (Preferred)
   ```python
   def _emergency_stop_obs():
       try:
           from src.engines.obs_engine import OBSEngine
           engine = OBSEngine()
           engine.connect()
           if engine.is_recording():
               engine.stop()
               logging.warning("[crash-guard] Stopped orphaned OBS recording")
           engine.disconnect()
       except Exception:
           pass
   ```
   - Rationale: `is_recording()` already exists, is used by `Pipeline._emergency_stop_engine()`, and handles edge cases.

#### Issue #3: STALL_THRESHOLD changed from 6 to 3 without plan documentation

**Description**: `STALL_THRESHOLD` was reduced from 6 to 3 in `recorder.py`. This changes existing nudge behavior — nudging now triggers after 4 polls (2 minutes) instead of 7 polls (3.5 minutes). The change is actually *necessary* for stuck-detection to work alongside nudging: with the original threshold of 6, the stuck abort (at 5 polls) would fire before the nudge (at 7 polls), making the nudge dead code. The reduction to 3 allows one nudge attempt before stuck detection aborts. However, this rationale is not documented in the plan or code.

**Location**:
- File: `src/capture/recorder.py`
- Lines: `17-19`

**Offending Code**:
```python
STALL_THRESHOLD = 3   # was 6
STUCK_THRESHOLD = 5
```

**Recommended Solutions**:
1. **Document the rationale in a commit message or PR description**
   - Explain: "STALL_THRESHOLD reduced from 6 to 3 so the nudge fires (at poll 4) before stuck-detection aborts (at poll 5). With the original threshold of 6, the nudge was dead code."
